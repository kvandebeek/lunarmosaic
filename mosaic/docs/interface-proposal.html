Interface proposal · for discussion

LunarMosaic

Two panel sets in, one editable two-layer image out. A luminance mosaic that defines the canvas, a colour mosaic matched to it, and a small set of controls that say plainly what each layer contributes. Built as a second application in the LunarAtlas family, from the same stylesheet.

Reference: kvandebeek/lunaratlas Tokens: lunaratlas/viewer/theme.css Pipeline: mosaic_builder.py · lunar_finish.py Design, not implementation
01

The workflow

Six steps, in a fixed order, each one a place you can stop and come back to. Steps 1–3 happen on the setup page, which looks like LunarAtlas's home and progress screens. Steps 4–6 happen on the canvas, which looks like LunarAtlas's viewer. There is no dashboard: the image is the interface.

STEP 1Import L

Drop the folder of mono luminance panels. Count, sizes and optics are read.

STEP 2Import RGB

Drop the colour panels as a separate set, with their own optics.

STEP 3Build both

Two independent mosaic builds, nine steps each, side by side.

STEP 4Match

The colour mosaic is scaled, turned and shifted onto the luminance canvas.

STEP 5Edit

A chain of blocks per path, a merge, then a final chain. Judged on 1:1 previews.

STEP 6Save & export

A project you can reopen, and a flattened TIFF or PNG.

The luminance mosaic is the canvas

Any mono capture can be the luminance — L, R, IR. Its pixel grid, size and orientation decide the result. The colour mosaic is always resampled onto it, never the other way round. Everything downstream reads in those pixels.

Colour is a layer, not a bake

Colour reaches the image through a Color blend over the luminance base, exactly as in Photoshop. Strength, saturation and smoothing stay live until you export.

Nothing is promised

The app says how well the two mosaics matched, in pixels, and shows where they did not. It never reports "aligned" as a state.

Sources are never touched

As the command-line tools already guarantee: panels are read, never moved, renamed or written. The project stores paths and numbers.

02

Home

The same shape as LunarAtlas's home: hero, one primary action, and your earlier work below it. The difference is that a LunarMosaic project is a thing you return to, so the list carries state rather than a solve status.

03

Importing the two sets

One card, two drop zones — one per stream, luminance and colour — side by side and clearly labelled by what took them rather than by file type. A stream can hold several sets at different scales (another Barlow, another telescope). Each set keeps its own optics, which is where the 2× Barlow on luminance and the bare RGB run get declared. A single set does not need them, and the app says so; a stream that mixes scales needs them, or confirms a scale ratio the app measured.

The sets are deliberately not symmetrical in the copy. Luminance is described as the thing that defines the canvas; colour as the thing that supplies hue only. That one difference, stated at import, is what makes the rest of the application predictable: a user who reads these two lines already knows why the output is luminance-sized and why colour can be blurred without hurting anything.

04

Building

Two builds, each the existing nine steps of mosaic_builder.py, shown as two independent stage lists. They are independent on screen because they are independent in fact: one can finish while the other fails, and the finished one is kept.

When a build fails

The failure is attached to the set that failed, the other set keeps its result, and the offered actions are the ones that can actually recover. Nothing already computed is thrown away: features, matches and poses are cached per set, so "Try again" resumes rather than restarts.

05

Checking the match

Each colour panel is registered directly onto the luminance mosaic with its own transform — a similarity, or an affine or cubic one where held-out points show it is needed. This is the step the interface must be most honest about, so it gets its own view mode rail and a chip in the status bar that is always visible afterwards.

The wording never claims success. The chip reads Match 0.6 px · worst 3.1 px, not "Aligned". Opening it gives the same popover treatment as LunarAtlas's quality explanation: a sentence in plain language, then the raw measurement.

06

The canvas and the two layers

The main screen. The image fills the window; one panel on the right holds both layers. Each layer is a row with a thumbnail, a name, what it contributes and a switch. Selecting a row opens its adjustments underneath it and closes the other, so the panel never grows past one screen.

Why these four controls

Every control on the colour layer already exists in lunar_finish.py and is named here the way an astrophotographer would say it. Nothing new is invented, and the advanced disclosure holds the rest.

Turning it off is the inspection mode "Colour only", and the switch does exactly that rather than producing a half-image.

07

Editing chains

The fixed adjustments in section 06 become a starting chain rather than the whole story. Each path — luminance and colour — carries its own ordered chain of building blocks; the two are merged; then a final chain runs on the merged image, because that is where you do levels, curves and unsharp mask today. Order is yours to change: drag a block up or down, switch it off, duplicate it. Any block can appear more than once — wavelets, then curves, then wavelets again — and each copy keeps its own settings.

One chain format for the app and the command line. The project stores the three chains as plain JSON — block type, parameters, enabled flag, order — next to the preview rectangles. lunar_finish.py becomes a chain runner that reads that file, so anything you build here can be re-run from a script, and your existing flags become a built-in default chain. Every block applies to the whole image, with one computed exception: any block can be set to fade out within a chosen distance of the limb. North-up is not a block: it is geometry. Previews and export share one orientation, but the pixels are turned once, after the chains, so every block works on the unrotated data exactly as PixInsight and Photoshop would.

Deconvolution is the one block that recovers detail rather than amplifying it. Wavelets and unsharp mask make surviving structure louder; deconvolution estimates the blur that destroyed it and inverts it. Its three PSF sliders are LuckyStackWorker’s, read from that application’s own code and reproduced: an Airy pattern (2·J₁(v)/v)² out to three times the Airy disk radius, then a log stretch ln(1 + I·D) — which is what diffraction intensity really is, a visibility control on the rings, not an optical quantity — then a Gaussian of σ = R·(5 − S)/16, which is what the seeing index does: 5 leaves the rings crisp, 1 smears them into a blob. Each channel uses its own wavelength (red 630 nm, green 532, blue 465), so the PSF is genuinely chromatic; a mono image uses 532 for all three. The block also accepts a measured PSF image. This is the most promising lead on the unexplained red edge excess in section 12, which is exactly a per-channel PSF difference.

White balance measures two places and corrects everywhere. As in PixInsight, it takes a background reference (the sky) to neutralise the per-channel offsets, and a white reference on the lunar surface to set the per-channel gains. Both default to automatic — sky pixels, and the highlands, which is what the builder already does at the end of every build — and either can be replaced by a rectangle you draw. Those rectangles only decide what is measured; the correction applies to the whole image, so this is not a mask. Measured against PixInsight: ColorCalibration makes the white reference neutral but puts each channel’s background back afterwards, so the sky stays tinted; BackgroundNeutralization in its default mode also rescales the whole image to fit — by 10–13 % — and ignores its target. On a raw 25 September limb panel, background preview, white limits 0.10–0.99, and both together gave the same colour to within 0.1 %; turning structure detection on left the highlands 1.5 % bluer. The block does calibration and neutralisation as separate, visible steps, matches PixInsight’s colour exactly, and never changes overall brightness silently.

Sub-pixel RGB shift finds the alignment itself. It runs twice, both times automatically. In the build, every panel’s R and B offsets against G are measured as it is read and corrected when they exceed about 0.1 px; the build log says what was found either way. As a block, it measures the image arriving at it and applies the shift, showing the dx and dy it found; LuckyStackWorker’s eight-way nudge pads adjust it from there. Detection uses two independent measures and only applies a shift when they agree: on the 25 September Saturn frame, channel centroids reproduced LuckyStackWorker’s correction to within 0.2 px, while phase correlation — which worked on lunar texture — was 1 px out on a smooth disk. When the two disagree the block says so and leaves the image alone. On the 25 September set both would find nothing to do: sampled across the 68-minute run, the channels sit 0.04 px apart with no drift, which is what AutoStakkert’s RGB align (always on) leaves behind. Where it earns its place is a night shot at prime focus without the ADC, or a stack where RGB align was off. It does not cure the coloured edges in that set: there, red features read about 0.2 px larger on every edge whatever its direction, which no shift can undo.

08

Incomplete colour coverage

The colour set will usually cover less of the disk than the luminance set. This is the one place where the two coverage choices live, and both are shown on the image before anything is written.

09

Saving and exporting

Two different actions, kept apart in the interface and in the words. The project is the thing you come back to; the export is a flat picture for everything else. Neither is PSD and neither is a layered TIFF, because neither is supported today and the design does not assume they will be.

Save project — ⌘S

Writes a folder name.lunarmosaic/ holding project.json: the panel paths, both mosaic layouts, the match transform and every adjustment, plus the two built mosaics as 16-bit TIFFs. Saves continuously while you work; the status bar says when.

Export image — ⌘E

Flattens the two layers as they look right now, at the luminance canvas's own resolution, into one TIFF or PNG. It is a result, not a document: reopening it gives you a picture, not layers.

Export the layers separately

For people who want to finish in Photoshop: the luminance mosaic and the matched, adjusted colour mosaic as two files on the same pixel grid, ready to stack with a Color blend by hand.

Observing site stays off by default. It is a checkbox in the export dialog, not a setting you forget. The Settings page repeats LunarAtlas's promise word for word: the location lives in your settings on this computer, is never sent anywhere, and is never written into an exported image or its metadata unless you tick that box for that export.

Everything above is the path where it works. These are the rest, and they are the part worth arguing about first, because they decide whether a four-minute build is ever lost.

12

Decisions still open

Two left. Everything else has been settled; it is listed under “resolved” below.

  1. How should daylight sky be removed?

    A daytime sky is not flat. The 4 October set kept a glow up to 11 % of the disk’s peak off the limb, because the builder subtracts one constant per channel. Fitting a smooth surface to the sky with the Moon masked out — as Siril does for starry fields — covers most of it, with two lunar catches. The sky glow lies on the disk as well, so the model has to be subtracted everywhere, not only around it. And the scattered light rises steeply towards the limb, which a smooth polynomial cannot follow, so the model needs a term that depends on distance from the limb. Per panel, before blending, is where it belongs, since each panel was shot under its own sky.

    Leaning: per-panel smooth model plus a limb-distance term, subtracted everywhere; then the sky is flat, and setting a black point just above its noise makes it pitch-black without clipping faint limb or terminator detail, which is where raising the black level by hand goes wrong today.

  2. What causes the coloured edges, if not misalignment?

    On the 25 September set every strong edge — limb, crater rims, terminator — shows red reaching about 0.2 px further into the dark side than green, in every direction. Matching the channels’ blur did not change it, only 0.08 px of it behaves like a shift, and AutoStakkert’s RGB align was on. That points at something tonal — a different response curve per channel, or AutoStakkert’s colour handling. It is not established, and no block is designed for it yet.

    Leaning: test a per-channel tone match on one panel before designing anything.

Resolved. The luminance input can be any mono capture — L, R, IR or anything else that carries the detail. Colour is not mosaicked separately: the luminance mosaic is built first, then each colour panel is registered straight onto it and blended there, so drifting refraction is corrected panel by panel and colour is resampled once. Measured on 25 September colour with the 3 px colour blur and ×2 saturation, a 1 px colour error is invisible; at 2–3 px a coloured rim starts to show at the limb, while the interior tolerates about 5 px — so the target is 1–2 px, which per-panel registration beats comfortably, and no mesh is needed. Built mosaics are kept in the project, with their size shown and one action to delete them. Colour never supplies detail where luminance is missing. Panel quality is one line per set. Any block can carry a “fade near the limb” setting — the one exception to whole-image blocks, computed from the limb and never drawn. Structure detection in white balance is off by default. North-up is applied once, after the chains. A stream may hold several sets at different scales; where luminance sets overlap, the one that resolves the finest detail — measured, not read from its pixel scale — wins. The app and the command line share the chain file. Blocks operate on stored values, may repeat, and include an automatic sub-pixel RGB shift. The merge is a Color blend with a strength slider. Both inputs are accepted however they were made.

Screens still to redraw to match. Section 04 builds the colour set as a second mosaic; it becomes a luminance build followed by colour panels placed onto it. Section 03 needs the single-colour-mosaic path and more than one set per stream, with the canvas size stated before building; section 05's match panel needs a per-panel table (placed or rejected, pose model, held-out residual); the editor needs a resolution view for mixed-scale luminance; section 09 must save the chains and previews, and chain presets are not yet drawn.
